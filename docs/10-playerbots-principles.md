# 10 · playerbots 的原理（机器人如何看、想、动）

> 前置：docs/06（配置与启动）、docs/07 §4（playerbots 上手三步——把小号带成 bot、发第一条密语）。本文是它们背后的原理篇：**bot 为什么会这样动、你从哪里下手动它**。与 docs/09（五个功能模块）不相干；命令全表与逐键配置说明见 playerbots 仓库 README 及其外部链接，本文只收经本 fork 源码逐一核对的一小批。

**版本边界**：本文一切断言只对本体系的 classic 1.12.1 fork 有效（全系列同一口径：以 fork 当前代码为准）。网上流传的 playerbots 教程多为 WLK 版/其他核心分支，命令面与行为差异很大，照抄容易踩空。文中出现的指令、策略名、表名全部可在 §10 的锚点表复核。

三个读书目标：

1. **控得更好**——知道行为从哪来，密语才发得准（§1-§3、§5）；
2. **配得出策略**——用游戏内的装卸语法和文本自定义，替 bot 编排打法（§4-§6）；
3. **有朝一日写副本首领策略**——看懂官方首领策略的"形状"、动手要动哪几层（§8-§9）。

> 全篇类比止步于直觉，不当规范；示例里的具体分值是机制示意，真实分值由各策略自行申报。

## 1. 分身：bot 是住在服务器里的无屏玩家

playerbots 不是客户端插件，也不是第二个程序——它整体编进 mangosd 服务端二进制里（挂载方式见 docs/02）。启动后，服务器在自己的进程里把一个**货真价实的角色**立起来：会话与角色规则和真人完全同款，唯一缺席的是"坐在屏幕前敲键盘的人"。这个位置由大脑（PlayerbotAI）顶上——世界走到它的这一拍，就问它一次"下一步干什么"。

```
   真人玩家                                bot 玩家
   ──────────                              ──────────
   屏幕/键鼠/插件                           （没有——不跑客户端、不占一条网线）
       │                                       │
       ▼                                       ▼
   把操作打成网络数据包                     没有数据包——
       │                                   由服务器世界循环直接驱动
       ▼                                       ▼
   WorldSession 会话   ◄── 完全同款 ──►     WorldSession 会话（socket 为空）
       │                                       │
       ▼                                       ▼
   Player 角色         ◄── 完全同款 ──►      Player 角色
                                               │
                                               ▼
                                         PlayerbotAI（大脑）
                                  每拍回答一次"下一步干什么"
```

由此推出本文最重要的一句话：**服务器不区分对面是不是人**。bot 能接任务、排本、下副本、上拍卖行，不是被开了特权，而是它在服务器眼里就是一个普通角色。

两类 bot、同一颗大脑：

- **小号 bot**——你账号下的其他角色，用 `.bot` 系命令挂成随从（docs/07 §4），听你密语；
- **随机 bot**——系统批量生成/上下线的"路人们"（数量与节奏见 §7），由一个总管排班；
- 它们只差"谁教"：小号被你教，随机 bot 按出厂配置运作——大脑同一颗，所以本文讲的一切对两类同样生效。

## 2. 一拍的心跳：它如何决定下一步

世界循环每隔一小段时间喂它一次（"一拍"，百毫秒级）。一拍之内大脑做五件事，顺序固定：

```
 一拍流水线

   ① 刷新记忆
      一堆带缓存的"传感器读数"按各自寿命更新：
      谁在打我、队友的血蓝、附近有没有危险物件……
        │
        ▼
   ② 巡逻触发器
      逐个检查条件；成立的发出"事件"——
      "队友濒死""我缺蓝""脚下有火"都是事件
        │
        ▼
   ③ 灌默认动作
      每个启用中的策略把"平时该做的事"
      （跟随、补 buff……）压进队列
        │
        ▼
   ④ 排队打分
      每件动作带一个"相关度"分——事件带来的动作
      通常申报高分（90/100 两档是官方常用写法），
      默认动作一般申报低分垫底；同名动作只留最高分
        │
        ▼
   ⑤ 按分执行
      从队首往队尾连试：轮到的动作先过"有用吗/可行吗"，
      不行就试队列里的下一个（备选与前置各有递补通道），
      第一件执行成功的办完即收——
      没被选上的过期作废，下一拍全盘重来
```

注意第 ⑤ 步的精确表述：**"办成一件就收"，不是"只做一件"**——一件失败会自动顺延备选。排查"bot 怎么愣住了"时这个细节有用。

新名词只有五个，全是日常语：

| 名词 | 一句话 | 牧师 bot 视角的例子 |
|---|---|---|
| 状态值 | 带缓存的传感器读数 | "队友血量""我的蓝" |
| 触发器 | 一个具体条件 | "队友血量跌过四成" |
| 事件 | 条件成立时发出的通知 | 【队伍有人濒死】 |
| 策略 | 一捆"触发器→动作"对应关系的包，随时装卸 | "治疗"策略 |
| 动作 | 最小可执行动词 | 施放快速治疗 |

一次仲裁演算（机制推演）

| 本拍进队 | 来源 | 申报分 | 结果 |
|---|---|---|---|
| 治疗 | 事件【队友濒死】 | ~80 | ✅ 执行（最高的可行动作） |
| 喝水 | 事件【我缺蓝】 | ~10 | 排在后面，本拍没轮到 |
| 跟随 | 默认动作 | ~1 | 垫底 |
| 躲火圈 | 反射层（§3） | — | 不排队——当场把正做的事打断再说 |

只要记住"**事件优先、默认垫底、办成一件就收**"，bot 八成的瞬时行为都能自己解释出来。

**为什么同配置的 bot 反应有先后**：每个触发器第一次巡逻的时刻被随机偏置（错峰启用），此后各自按节流间隔巡逻——两只一模一样的 bot 也绝不同步举手。这是刻意设计：既防全体同一拍挤占性能，也顺带添了点"人味"。

## 3. 四台引擎与一位守夜人

上面那台流水线不是一个引擎，是**三台互斥的决策脑 + 一层独立的反射**：

```
        ⏰ REACTION（反射层，守夜人）
        每一拍都醒着，不在轮换里——
        磕药、躲 AoE、回密语……先斩后奏，
        必要时直接打断正在读的条/正在走的位
                    │（随时插队）
     ┌──────────────┼──────────────┐
     ▼              ▼              ▼
 COMBAT 战斗脑   NON-COMBAT 平时脑  DEAD 躺尸脑
 （打起来时）     （没在打时）      （躺了）
     └── 三台互斥轮换：同一时刻只有一台发号施令 ──┘
```

为什么要独立的反射层？反着想：躲技能若走主流水线——等轮到、去排队、办成一件才收——永远慢半拍。所以引擎把"保命类小事"放进一个**每拍都醒着、拥有打断权**的小脑里。像手碰到烫锅缩回来——不走大脑。

对下副本的直接意义：bot 能在读条间隙躲开地上的火，恰恰因为"躲火"不走决策主流程——它是反射。反射层出厂装着这些小包：回复密语与闲聊、躲开 AoE 一类伤害区（含指定的个别怪）、自动磕药，外加一个副本路由用的常驻包（§8 再见到它）。

两类 bot 的反射层内容出厂相同；要装卸用 §5 的 `react` 前缀。

> 四台引擎各自的**出厂行动目录**（每台装什么包、装上后看见什么、九职业默认包速查）见 `docs/11-playerbots-engine-actions.md`。

## 4. 一切皆是名字

最短的一节，全篇的枢纽。

引擎里四类东西——策略、触发器、动作、状态值——**全部以字符串名字注册**。每个 bot 的"名字全集" = 通用上下文 ⊕ 自己职业上下文：

```
  通用上下文（人人一套）                职业上下文（该职业额外加）
  "follow" "stay" "threat"              "frost" "shadow" "protection"…
  "conserve mana" "avoid mobs"…
             └────────────┬────────────┘
                          ▼
           这个 bot 的名字全集（四本花名册：
           策略/触发器/动作/状态值 各一册）
                          │
                          ▼
          运行时用 +/−/~ 按名组装"当前策略集"
            例：+follow（顺手顶掉互斥的 stay）
```

为什么值得单独一节——"名字"是贯穿所有定制层的通货：

- §5 你在密语里装卸的，是名字；
- §6 你在文本里搭桥用的，还是名字；
- §9 你将来写 C++，最后一行同样是"注册一个新名字进某本花名册"。

顺带解答一个高频困惑：策略名**小写、区分大小写、一字不差**（注册表按字面匹配，不做模糊与归一化）——`+DPS ASSIST` 无效，合法写法是 `+dps assist`（§10 有锚点）。

策略像 U 盘：即插即拔、职业包叠在通用包之上、有些插口互斥（`follow` 与 `stay` 同槽——插一只自动顶掉另一只）。**别用乐高做类比**：乐高暗示"任意拼出新东西"，但策略拼不出花名册里不存在的新反射——这是 §6 的硬边界，先按下。

## 5. 会说话就会编程：控制面

你已经会一句话编程了：docs/07 的 `/w <bot> follow`，本质就是"把名字 follow 装进这个 bot"。本节把它展开成完整语法。

**装卸语法**（对四台引擎各自生效；名单用逗号连写）：

```text
+名字     装上
-名字     拆下
~名字     有则拆、无则装
```

**四台引擎的指令前缀**：密语发 `co …` 只操作战斗脑；`nc …` 平时脑；`de …` 躺尸脑；`react …` 反射层；`all …` 四台一起。例：

```text
/w <bot> co +dps assist          （战斗脑加"DPS 助攻"）
/w <bot> all +molten core        （四台同挂 MC 路由包——§8）
/w <bot> co ~conserve mana       （省蓝包，toggle）
```

**@ 前缀群广播**（说在说/团队频道里，只有命中前缀的 bot 执行；前缀家族覆盖坦克/治疗/近战/远程/单个职业/等级段/小队等）：

```text
@tank tank attack                （让坦克面 bot 去顶当前目标）
@mage  co +frost
```

**策展命令子集**（全部经源码核对；全表以仓库 README 为准）：

| 意图 | 指令（密语发给 bot） |
|---|---|
| 走位 | `follow` `stay` `guard` `free` `wander` `flee` `grind` |
| 打架 | `attack`（打我当前目标） `attack rti`（打标记目标） `pull` `tank attack` `cast` `castnc` `max dps` `save mana` |
| 组队 | `invite` `join` `lfg` `give leader` `formation` `stance` `ready`（就绪确认） `revive` `self res` `boost target` |
| 任务 | `q` `quests` `quest reward` `share` `accept` `drop`（弃任务） |
| 装备/天赋 | `e`（穿） `ue`（脱） `c`（点包） `u`（用） `keep` `talents` `trainer` `sendmail` `ah`（拍卖行） |
| 排障/信息 | `stats` `where` `who` `rep` `ll`（战利品清单） `add all loot`（拾取全场掉落） `avoid creature` `release` `teleport` `taxi` `repair` `home`（炉石） `summon` `debug` `help` |
| 策略 | `co/nc/de/react/all ±名字`；`reset strats`（回出厂） `reset ai` `save ai` / `load ai`（存/取整套） `list ai`（列名） |

fix: 《help》typo → `help`. 

**策略随角色走**：装卸会自动落进角色库的一张存档表（docs/08 迁移时随整库走的就是它），重登不丢；`save ai`/`load ai` 可额外存取整套。

**为什么 bot 偶尔"不听话"**（按出现频率排）：

1. **名字不合法**——大小写/拼写错（§4 末）；
2. **互斥顶替**——后装的把先装的顶了（刚 `+follow`，又有人/自己发了 `stay`）；
3. **真在忙**——这一拍被更高分的事占满（§2 演算），下拍就轮到；
4. **反射层插队**——它先活命，那是设计。

复位三板斧：`list ai` 看现状 → 找到肇事名 `co -肇事名` → 搞不定 `reset strats` 回出厂再教。

> 装卸是否真的改变了行为，怎么搭台验证？→ `docs/12-playerbots-strategy-testing.md`。

## 6. 文本自定义策略：不写代码的"写策略"

§5 只是开关现成策略。想把"当什么发生 → bot 干什么"自己搭桥，引擎提供**文本层**：在你的角色库里写几行"触发器 → 动作"，注册成一个新的策略名（官方叫 custom strategy）。装上后与官方策略同权参与 §2 的排队。

- **存在哪**：角色库一张表 `ai_playerbot_custom_strategy`，每行一条规则；`name` = 策略名、`idx` = 行号、`owner` = 归属（指向某 bot 则是它专用的版本，**0 = 全体共用**）。
- **怎么写**：最顺手的是游戏内密语 `cs`——写完**当场生效、免重启**；SQL 直改这张表也行，等下一次装载时生效。

**一行规则的格式**（三个符号：`>` 分界条件与动作、`!` 标分、`,` 并列下一个动作）：

```
 一行规则 = 触发器 > 动作1[!分值] , 动作2[!分值]…

 出厂示范 say 的第 1 行：
   critical health > emote::helpme!99 , say::critical health!98

   critical health        触发器名（引擎既有名字：有人濒死）
   >                      条件与动作的分界
   emote::helpme          动作1 —— 做表情求助；::后面是给动作的参数
   !99                    动作1 的申报分（排队很靠前）
   ,                      并列——前一件没成时按序递补
   say::critical health   动作2 —— 开口喊话（参数即说的话）
   !98                    动作2 的申报分
```

参数的含义由动作自己解释（表情名/喊话内容/物品名……）：**仿写时先沿用出厂行出现过的形态**，新参数是否被接受取决于该动作的实现。

**cs 三板斧**（以出厂示范 `say` 为例）：

```text
cs say                          → 看 say 有几行
cs say ?                        → 逐行看内容
cs say 7 critical health > emote::healme!99   → 写入/覆盖第 7 行
（某行想删：把该行内容传空）
```

**挂上去**：写好的 custom 仍是个策略名——`nc +custom::say`（平时脑装示范品；按触发语境也可用 `co +` / `react +` 选脑）。**随机 bot 出厂默认带着 `+custom::say`**——你改公共版 `say` 的规则，全服随机 bot 的"嘴"当场改变。

**硬边界（全篇最重要的"不能"）**：文本层只能**引用既有名字**——触发器、动作、参数都来自花名册。想造一个新条件（"认出这个怪的火圈往哪跑"）或新动作，文本里写不出——**撞墙之处，正是 §9 C++ 的起点**。

> 文本策略的实测闭环（`cs` 写行→热生效→造状态诱发→看播报）见 docs/12 场景 6。

## 7. 配置地图：不进游戏也能调的事

前面都在游戏内动手；这一层是**服务器主人**的——`run/etc/aiplayerbot.conf`（本体系由流程 06 生成）加角色库几张运行时表。

先看"随机 bot 的生命表"——它们不是被定时批量处理的，而是**每只 bot 身上挂着一只只小闹钟**（存在表里）：到点上线、到点下线、到点重铸（等级/装备/天赋全部重掷一遍）、到点换打法、到点传送换图、到点对齐"期望在线数"。闹钟由总管逐拍处理——你看到的"路人常换常新"就是它的外显。排本意愿也存在配置里，开着时真人开组会有 bot 补位、甚至体面地把队长交给真人（交互细节以实测为准）。

conf 六族（族内键不逐枚举——开文件认得归类即可）：

| 族 | 管什么 | 概念级用途 |
|---|---|---|
| 总开关/特性 | 模块开关、指令前缀等 | 基本不动 |
| 随机 bot 生命周期 | 数量/等级段/上下线节奏/传送 | 世界"人口政策"（数量大将吃内存——docs/06 已提示） |
| 职业种族配比 | 各职业/阵营占比 | 想看满街萨满就动它 |
| 出厂策略 | 四台引擎各自默认装哪些包 | §5 `reset strats` 回到的就是这里 |
| AI 手感 | 拍间隔/反应延迟/每拍尝试预算/视距 | "变笨省 CPU ↔ 变敏费 CPU" |
| 聊天风味 | 喊话概率/整活文本（含著名的风剑 Thunderfury 梗回复率） | 世界的"烟火气"旋钮 |

改 conf 重启生效；改表内容下一轮装载即生效。装备评价与路网两张表见 §9 的"免编译岔路"。

## 8. 副本与首领：以玛格玛达尔为师，奥妮克希亚是空盒子

带 bot 进本，你什么额外都没做，它们也已经"能打"——那是 §4 通用上下文的功劳（躲/打断/打杂，样样有通用包）。副本策略是叠在其上一层**特化**：一进指定地图自动激活，离图自动收摊。全程没有一个字需要你配。

以玛格玛达尔（MC 一号 boss）走一遍接力——全模块唯一满配的老板级示范，值得逐站看：

```
 ① 进本            踩进熔火之心那一刻
                      │ 触发器认出"这是 409 号地图"
                      ▼
 ② 挂副本包        出厂常驻的"dungeon"路由包自动给全队叠上
                      │  "molten core" 模式（副本键=策略名）
                      ▼
 ③ 开战            有人打到玛格玛达尔
                      │ 触发器 "start magmadar fight"（认 11982 号怪）
                      ▼
 ④ 挂 boss 包      战斗脑叠入 "magmadar" 首领包，从带起这些新反射：
                      · 脚边刷出岩浆炸弹 → 反射层【躲】（认 177704
                        号机关，半径 5 码）
                      · 它贴脸了而我是奶妈/远程 → 战斗脑【拉开 31 码】
                      · 火抗药备着 → 战斗脑【磕】
                      （平时脑另有杂活：路过未熄火盆 →【去熄】）
                      ▼
 ⑤ 收摊            战斗结束 → "end magmadar fight" → 自动 -magmadar
                      │ 首领包撤下，回到常规模式；离图连副本包一起卸
                      ▼
                  （调试自己写的包时才需要手挂：co +magmadar）
```

逐站会发现一个事实：**首领包里没有一行自己的移动代码**——"躲"“拉开距离"全是复用引擎现成的移动原语，新东西只有"认出哪个怪/哪个机关"的触发器。这是它能当模板的原因。

**内置副本覆盖盘点**（副本键如实标注）：

| 副本键 | 内置内容 |
|---|---|
| `onyxia's lair` | **空盒**——进门路由与开战开关在，首领战斗体整个是留白注释（官方到此一游） |
| `molten core` | 玛格玛达尔满配（上图全部）+ 熄火盆杂活 |
| `blackwing lair` | 无首领；只有压制室专区——盗贼隐身拆机关，且该区内盗贼的其他动作被一律清零专心拆弹（倍率器的一次漂亮实战，§2-④ 的"加权/否决"具象） |
| `naxxramas` | 仅四骑士一条：躲开脚下的虚空区域 |
| `karazhan` / `mechanar` | 键在、代码在——TBC 的图，经典客户端进不去（在场但不生效） |
| （祖格 / AQ） | 连副本键都没有——bot 用通用打法打杂兵，首领≈裸打 |

**「路由 ≠ 内容」**是上表最想让你带走的一课：进本认图、开战挂包的**框架**六副本一体通用；挂上的包里**装没装行为**是另一回事。Onyxia 的空盒不是 bug——它是一张空好的施工图，等人在 §9 动手。

文本层可以先行补一块：`custom::onyxia` 这类自定义包与编译进的同名空包并存不冲突——复用既有触发器能拼出"躲某某 AoE"级的反射；但"认出是哪个技能/往哪躲"的新名字仍要 C++。**文本=揩既有能力，C++=造新能力**。

> 这条接力链的完整工位排演（造副本图、造 boss、造炸弹全用 GM 命令）见 docs/12 场景 5。

## 9. 从文本到 C++：定制首领策略的最短路径

三级跨步：

| 你想 | 层 | 成本 |
|---|---|---|
| 装卸现成打法 | 密语 +/−/~ | 零 |
| 用既有积木搭"条件→动作" | §6 文本 | 低，不重编 |
| **造新积木**（新触发器/动作/策略） | 改 playerbots 源码 + 整编 | 一次到位 |

**什么时候必须进 C++**：条件或动作在名字全集里没有——要认新的怪/技能/机关编号、要新走位新连招。反之花名册里够用，就坚决留在文本层。

**动手的形状**（照抄 Magmadar；§8 的图就是施工图）：

1. **触发器对**——进本认图/遭遇认怪/结束三件套，外加你需要的机关感知（火圈那种"认编号 + 半径"）；
2. **动作对**——"挂包/卸包"两个开关动作 + 应对动作（躲/拉开——几乎总能复用引擎现成移动原语）；
3. **策略对**——把触发器与动作串成"条件→动作"的包，并挂进副本路由；
4. **四处注册**——触发器/动作/策略三本花名册 + 副本路由，各添一行"注册名"（§4 的名字体系在源码里的最终落点就是这几行）；
5. **整编一次**——构建脚本按通配收源文件，新文件**不用登记**；重启进程载入，**不动数据库**；开发期随时 `co +你的首领名` 手挂手卸，与 §5 完全同语法。

本文到此为止、不给文件骨架——那是将来另一篇 how-to 的事；届时按 §10 锚点里玛格玛达尔三件套逐文件对照，一次上手。开发期的手挂手卸与验证手段都在 `docs/12` 的工具箱与场景里。

**三条免编译岔路**（能不改码就不改码）：

- **weightscales 装评权重表**——bot 判断"哪件装备对我更好"的全部依据，就在世界侧一组可改的表里；改表即改即用（这组表 docs/08 §2 提过装库来源）；
- **travel_nodes 路网表**——bot 远行的"公路网"，同为世界侧数据（想让 bot 绕开哪、抄哪条道，改图不改码）；
- **conf 出厂策略**——想让全服 bot 自带某个打法（如人人省蓝）：出厂族一行即改，比逐个密语教持久得多。
